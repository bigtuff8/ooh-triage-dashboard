SECTION: Part 1 — server changes (E1 automatic call record, A1 ticket page)
The call record starts automatically at site confirm (POST /api/sites/:siteNo/confirm now returns a callId). The browser sends its progress to POST /api/calls/:id/progress after every step. The call is finalised by the agent pressing End call or Raise another issue, by leaving the screen, or by the idle sweeper after 20 minutes. Finalising an issue with a ticket appends an [OOH CALL RECORD] internal comment to that ticket. Finalising an issue without a ticket, or a call with no issue at all, creates a contact-history ticket already solved (tagged ooh_call_record). Idempotency: a second finalise of the same issue writes nothing. The idle sweeper is an unref'd setInterval in the existing server process. A new service (services/call-record.js) holds the in-process call map, the idempotency logic and the Cosmos persistence. The in-app ticket page (GET /api/tickets/:id/view) returns subject, plain-English status, P1 badge, created/updated times and the OOH comment thread. The ticket page route at /ticket/:id is served by the existing server and renders renderTicketPage in app.js, always in a new tab. The in-process call map also supports services/store.js for best-effort Cosmos durability. Progress write failure tolerance: POST /api/calls/:id/progress writes are fire-and-forget. A failed write is logged at warn level and the step remains recorded in-memory. On a call resume (same-operator reopen) the in-memory steps are available for replay. If the pod restarts without OohCallRecords present, steps since the last successful Cosmos write are lost. This is an accepted boundary condition and is not retried by the browser. The worst-case effect is bounded to the steps since the last successful write, which is typically one step.

SECTION: Part 2a — browser heartbeat and same-operator resume
The browser sends POST /api/calls/:id/heartbeat every two minutes while the call record is open. The server writes lastHeartbeatAt to the Cosmos call record. The idle sweep reads lastHeartbeatAt from Cosmos (not from the in-memory lastActivityAt field) and only marks a call as a finalise candidate when the durable timestamp is beyond the 20-minute threshold. A live call with the agent waiting on the customer generates a heartbeat every two minutes and is never swept. The heartbeat runs unconditionally, regardless of document.visibilityState: the agent may switch between tabs during a P1, and heartbeats must continue. If a call is swept in error (for example a brief network drop caused a heartbeat gap), same-operator resume handles recovery. When an agent returns to the same site within two hours, the confirm response includes a sameOperatorResume flag and the previous call's id; the app offers "Continue this call" before starting a new record. Pressing Continue calls POST /api/calls/:id/reopen and the existing record is re-opened.

SECTION: Part 2b — durable idle sweep with conditional write
The idle sweep (sweepIdle in call-record.js) runs once per minute as today, but its finalise decision uses the Cosmos-durable lastHeartbeatAt rather than in-memory lastActivityAt. For each candidate call, the sweep does one Cosmos point-read to fetch the current lastHeartbeatAt. Only if that durable value also exceeds the threshold does the sweep proceed to finalise. The finalise write uses an ETag-conditional upsert (the store.js ifVersion parameter) so two replicas racing cannot both finalise the same call. This design is correct at any replica count. At OOH volumes (tens of concurrent calls at most) the point-read per candidate per sweep tick is negligible. The in-memory lastActivityAt continues to be updated on every step write, but it is used only as a first-pass candidate filter, never as the sole basis for the finalise decision. Failure posture: sweepIdle() wraps every Cosmos point-read in a try/catch. On any failure (network error, Cosmos unavailable, 404), the sweep skips that candidate for this tick, logs the skip at warn level, and continues to the next candidate. It never falls back to in-memory lastActivityAt as a sole finalise trigger; that choice is deliberate to avoid losing the ETag race guard under a degraded Cosmos call. This is explicitly fail-safe: a call is only finalised when the Cosmos read succeeds and the durable timestamp confirms the threshold. If Cosmos is persistently absent, candidates accumulate in-memory without being swept, which is bounded by the hard call-lifetime cap. Hard lifetime cap: regardless of heartbeat state, any call whose startedAt timestamp is more than 8 hours old is finalised by the sweep with reason 'max-lifetime'. This caps Cosmos writes from open tabs left unattended and bounds the worst-case accumulation when Cosmos is degraded.

SECTION: Part 2c — pagehide finalise and in-tab recovery banner on 409
The left-screen finalise uses the pagehide event (persisted: false), not visibilitychange. visibilitychange fires when the agent alt-tabs or opens the override guide in a new tab, which is the expected behaviour during a P1; it must never trigger finalise. The pagehide event fires only when the tab is actually closing or navigating away. The heartbeat is not gated on visibility and continues while the tab is backgrounded. If the idle sweep finalises a call in error while the tab is still open (for example a brief network drop caused a heartbeat gap), subsequent writes from that open tab arrive on a finalised record. The server distinguishes two cases. A known duplicate (the same issueKey already on the finalised record) returns 200 already, a silent no-op. An unknown issue arriving on a finalised record from the same operator within two hours returns 409 Conflict with reason: call-already-finalised and the callId. On receiving the 409, the browser shows a non-blocking in-tab recovery banner below the site header reading "This call was saved automatically — if you need to add anything, click Continue to reopen it" with a single Continue button. The button calls POST /api/calls/:id/reopen. Writes are queued in the browser while the call is in the disconnected state; on reopen they are replayed in order. If the agent ignores the banner and closes the tab, the already-saved record stands.

SECTION: Part 2d — IDOR scoping on the ticket-view endpoint
GET /api/tickets/:id/view currently requires sign-in only. The build adds three-layer server-side scoping evaluated before any Zendesk API call. First, the ticket must carry the ooh tag, which is verified by calling Zendesk and checking ticket.tags. Tickets without it are rejected with 403. The ooh-tag Zendesk call is fail-closed: if the Zendesk tags API call fails for any reason (timeout, 503, network error), the endpoint returns 403, never a pass-through 500 or a silent success. This prevents Zendesk degradation from opening a cross-operator access breach. Second, the ticket must be linked to a call record owned by the requesting operator (the in-memory calls map has the ticketId for any issue the operator raised a ticket for), or the ticket's siteNo must match a site the operator has currently confirmed. Third, if the operator has a live call record, the ticket's siteNo must match that call's siteNo. All scope failures return 403, never 404 on an auth failure, to prevent an authenticated agent from using the error code to confirm whether a ticket exists. The ticket page at /ticket/:id is likewise enforced server-side by auth middleware: unauthenticated requests receive a redirect to sign-in, not a 401. The PowerPause guide at /guides/powerpause-contractor-info.html is a static file under public/guides; the build adds a middleware guard so unauthenticated requests are redirected to sign-in.

SECTION: Part 2e — ticketStatusMap closed list and output encoding
The ticketStatusMap is the STATUS_TRANSLATIONS object in services/zendesk.js, already populated with every known Zendesk custom status id. The build makes it a strict closed list: any value outside the left column maps to the generic fallback "Being handled by the IoT team" rather than surfacing the raw Zendesk status string. Specific fallbacks: a merged ticket (status closed, merged tag present) shows "Merged with another ticket — being handled by the IoT team"; a deleted ticket (Zendesk 404) shows "Ticket no longer available"; a Zendesk API error or timeout shows "Status not available right now". None of these ever link the agent to Zendesk. Output encoding covers five free-text sinks. DOM writes in app.js, flows.js and views.js: every insertion into innerHTML must use the existing esc() helper or switch to textContent/createElement; direct DOM writes must never concatenate unescaped user-typed strings into innerHTML. Server-rendered HTML (the screen dump, confirmation cards, the ticket page): every variable passed to a template is HTML-entity-encoded via a confirmed escaping helper before insertion. Zendesk comment bodies: free-text values (agent notes, timetable fields, the "not-on-our-list" equipment name, the caller's words) are code-fence-wrapped before insertion to prevent Markdown injection. The build lead signs off the encoding audit as a merge pre-condition. Regression guard: a unit test is added that statically scans the source of app.js, flows.js, views.js and server.js for innerHTML assignments containing a dollar-sign (variable interpolation syntax) that are not immediately preceded by an esc() call. The test fails if any such unguarded sink is found. This pins the encoding audit mechanically in the CI suite and prevents a future edit from silently re-introducing an unescaped sink.
