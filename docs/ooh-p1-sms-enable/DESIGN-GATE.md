**Release:** OOH Triage Dashboard — R1, Stream B · **Stage:** Design · **Ticket:** OOHDASH-73 · **Date:** 2026-09-23
**Repo (verified):** `C:\repos\ooh-triage-dashboard` (owner bigtuff8), app v1.2.4, `SMS_PROVIDER="log"`, `WRITES_DISABLED="true"`.
**Input:** the signed-off, merged discovery gate `docs/ooh-p1-sms-enable/DISCOVERY-GATE.md`, and the cross-stream verdict `docs/project/releases/CROSS-STREAM_cellar-vs-p1-sms.md` (Streams A and B fully independent).
**Method:** every code claim below is traced to a file and line in the working tree. No code, config or secret is changed by this artefact; it specifies enablement, it does not perform it. No secret values appear — credentials are named by key only.
**Mockup:** `docs/ooh-p1-sms-enable/mockups/p1-outcome-card.html` — the P1 outcome card in all three states (log / twilio / fail-closed), built from the live CSS.

Nothing in this stream writes application code. This is canary **go/no-go #4 (Q-F)** and enables **no device write** — it sends texts only.

## 1. The exact enablement change set

**Gateway decision (proposed — pending James's confirmation at gate): reuse the existing Airedale Twilio account and sender number** that the IoT Support Dashboard already uses in production. Rationale: the send path already targets the Twilio REST API directly via `axios` (`escalation.js:37-41`) with no SDK, so Twilio-reuse is a **zero-code-cost** enablement; any other provider would require a new branch in `sendViaProvider()` (a code change) plus a fresh account, for no operational gain. This is the recommendation unless James rules otherwise (see open decisions, §7).

**Accepted coupling risk (named, not inherited silently).** Reusing the existing Airedale Twilio account **couples OOH with the IoT Support Dashboard**: they share the same account-level rate limits, the same auth-token rotation (rotating the token for one affects both), and any account-level action (suspension, billing hold, sender-number change) hits both products at once. This design **explicitly accepts** that coupling as the cost of a zero-code-cost enablement — it is named here so it is a chosen trade-off, not an unexamined inheritance. **Decoupling option if it ever bites:** provision a dedicated OOH Twilio subaccount or a separate Messaging Service, which isolates rate limits and rotation at the price of a new account to manage (still config-only, no code change). Out of scope for this stream unless James directs otherwise.

**Change 1 — the five secret values loaded into `ooh-dashboard-secrets` (Spencer).** Referred to by key NAME only; no values in this document. The three Twilio credentials the chosen gateway needs:

- `TWILIO_ACCOUNT_SID` — the Twilio account id (read at `config.js:102`).
- `TWILIO_AUTH_TOKEN` — the Twilio auth token (read at `config.js:103`).
- `TWILIO_FROM` — the sender number the text is sent from (read at `config.js:104`).

The two recipient values that make the text correct and deep-linked:

- `ESCALATION_ONDUTY_NUMBER` — the on-duty recipient number (read at `config.js:106`). Single static recipient; there is no rota logic in the code, and a schedule-driven rota is out of scope for this enablement (see §6 for the named owner and the manual rotation runbook that governs this value, and the future-enhancement note).
- `ESCALATION_ONDUTY_NAME` — the recipient display name (read at `config.js:107`; defaults to "On-duty escalation manager" if unset). This name is the only recipient identifier ever shown or persisted, so it **must be set to a real person's name** at load time — never left to the generic "On-duty escalation manager" default, which would make the outcome card, the log and the Zendesk comment unable to tell the handler *who* was actually texted. A real name is a required part of Spencer's secret load, confirmed in writing (see §2 Step 2) and owned/rotated by IoT Support (see §6).

**Change 2 — confirm the deep-link host.** `IOT_DASH_BASE_URL` (read at `config.js:113`) must be set to the **live** IoT Support dashboard host so the deep-link `${base}/?ticket={id}` (`escalation.js:29-31`) resolves to a real ticket. Note the code default is the UAT host (`config.js:113`), so this must be explicitly set in the secret, not left to default. This is a confirm-in-place, not necessarily a new load.

**Base-URL correctness is NOT covered by the fail-closed guard — this is a precise, load-bearing distinction.** The credential guard at `escalation.js:36` checks **only** `accountSid || authToken || from`; it does **not** inspect `iotDashBaseUrl` at all. `iotDashBaseUrl` is consumed unchecked at `escalation.js:30` to build the link. So if `IOT_DASH_BASE_URL` is wrong or still points at UAT, `sendViaProvider()` does **not** throw: the text sends, Twilio returns 2xx, `dispatchOk` becomes **true**, and **no** `sms-dispatch-failed` alert fires — a **silent broken/wrong deep-link**, not a fail-closed. This means the earlier "if any value is wrong the code fails closed" framing is **too broad and is corrected here**: only **credential** failures fail closed; **base-URL** correctness does not. It is mitigated two ways, both required: (a) Spencer's written confirmation (§2 Step 2) that `IOT_DASH_BASE_URL` = the **live** host; and (b) the **required** live-test check that the received SMS link, when tapped, opens the **correct** live ticket (§4 pass criteria). **Future hardening (out of scope now — a code change):** extend the guard/startup checks to validate that `iotDashBaseUrl` is set and is not the UAT default before enabling twilio, so a wrong base URL also fails closed rather than silently sending a dead link.

**Change 3 — the provider flip (James self-serve).** `SMS_PROVIDER` from `"log"` to `"twilio"` — one line, `k8s/deployment.yaml:76-77`, applied live via `kubectl set env` and committed to git. This is the single functional switch; everything else is credentials the switched-on code then reads.

**What is NOT changed:** no application code; `WRITES_DISABLED` is untouched (`deployment.yaml:74-75`); no device-write path is enabled. The honesty test suite (`test/p1-dispatch-honesty.test.js`, OOHDASH-72 / Test 11c) must stay green. Its existing State C assertions are not altered; the one permitted addition is a **companion test case** for the missing-credential guard-throw half of State C (§3/§4) — an additive test that strengthens the fail-closed proof and touches no application code.

## 2. The ordered rollout runbook — access split explicit, fail-safe sequencing

The two changes have two different owners, and the order is a safety property, not a preference. The memory pod-roll finding governs it: James's scoped account holds the env-patch verb (so `set env` is self-serve) but **cannot read or write secrets** (so the credential load is Spencer's). There is **no CI that applies the manifest**, so a git-committed change alone has zero live effect — only `set env` reaches the cluster, which is why each live change is also committed to git to close the git-versus-cluster drift.

**Step 1 — Spencer loads the secret (hard external dependency, FIRST).** Load the five values (§1 Change 1) into `ooh-dashboard-secrets`, and confirm `IOT_DASH_BASE_URL` points at the live host (§1 Change 2). James's account cannot do this step. Nothing is live yet — the running pod still has `SMS_PROVIDER=log`, so the app is unaffected while the secret is populated.

**Step 2 — Spencer confirms the secret load IN WRITING (communication checkpoint, not a technical verification).** James **cannot** technically verify the secret before the flip: his scoped service account has no secret-read access, and the running pod does not reflect new `envFrom` values until it is rolled — which only happens at the flip. So the pre-flip gate is a **written confirmation from Spencer** that all **six** values are loaded into `ooh-dashboard-secrets`: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`, `ESCALATION_ONDUTY_NUMBER`, `ESCALATION_ONDUTY_NAME` (a **real person's name**, not the default), and `IOT_DASH_BASE_URL` pointing at the **live** IoT Support host. James does not flip until that written confirmation is in hand. Be explicit about the limit of this step: the earliest **technical** confirmation that every value is correct is **post-flip** — the pod roll picks up the secret and the §4 live test proves it end to end. Be equally precise about what the safety net catches: if a **Twilio credential** is missing or invalid, the code **fails closed** to the "phone the manager now" card and raises `sms-dispatch-failed` (see §3, State C). But a wrong `IOT_DASH_BASE_URL` does **not** fail closed — it sends a text with a dead/wrong deep-link and reports `dispatchOk:true` (see §1 Change 2). So Spencer's written confirmation must specifically include that `IOT_DASH_BASE_URL` = the **live** host, and the §4 live-test deep-link check is the required catch for that value. The credential fail-closed net is what makes a pre-flip written confirmation an acceptable gate **for the credentials**; the base URL relies on the written confirmation plus the deep-link test, not on fail-closed.

**Step 3 — James flips the provider (self-serve, ONLY after Step 1).** `kubectl set env deployment/ooh-dashboard SMS_PROVIDER=twilio` in namespace `iot-services`. Flipping BEFORE the secret is loaded is a **safe, visible failure** (the code fails closed on missing credentials — see §3 State C), not a silent one, but it is not "enabled" and it will raise an alert, so do not do it out of order.

**Guardrail — the flip touches exactly ONE key, and that key is never `WRITES_DISABLED`.** The `kubectl set env` command **must** set **only** `SMS_PROVIDER=twilio` and **must not** include `WRITES_DISABLED` (or any other key) in the same invocation. This is the known Stream-B-versus-write-flip manifest touch-point made concrete: `WRITES_DISABLED` sits directly adjacent to `SMS_PROVIDER` in the env block (`deployment.yaml:74-77`), so a copy-paste or a multi-key `set env` is an **accidental device-enable risk** — enabling SMS must never, as a side effect, enable a device write. **Named risk:** an accidental `WRITES_DISABLED=false` in this command would silently arm the device-write path this stream is explicitly independent of. **Verification (required):** immediately after the flip, confirm the command changed a **single** key — e.g. inspect the resulting deployment env and confirm `WRITES_DISABLED` is unchanged (still `"true"`) and only `SMS_PROVIDER` moved to `twilio`. If more than one key changed, treat it as an incident and roll back both.

**Step 4 — Commit the manifest line to git as applied.** Change `k8s/deployment.yaml:77` from `value: "log"` to `value: "twilio"` and commit, so the audit trail and the running cluster agree and a future full re-apply cannot silently revert the flip. This is a Stream-B-only edit; note for later that `WRITES_DISABLED` (line 74-75) sits directly above and is the eventual write-flip's line — a Stream-B-versus-write-flip merge touch-point, not a concern for this step.

**Step 5 — Run the live test (§4) before declaring the P1 SMS live.** "Live means in effect, not merely wired" — the flip alone is not proof.

**Abort / rollback (single self-serve action).** If anything is wrong, `kubectl set env deployment/ooh-dashboard SMS_PROVIDER=log` returns the system to today's safe no-send behaviour immediately (a pod-roll; abort SLA equals pod-roll time), and revert the git line to match. No secret needs to be removed to abort — with the provider back on `log`, the loaded credentials are simply unread. Rollback enables nothing and loses nothing.

## 3. Code behaviour at each state (build-ready, verified to file:line)

The same code serves all states; only `SMS_PROVIDER` and the presence of credentials differ. The mockup renders all three.

**State A — log mode (today).** `sendViaProvider()` takes the non-twilio branch (`escalation.js:44-47`): it logs a "would send" line and returns `{ provider:'log', sent:false }`. Back in `escalateP1`, `entry.dispatchOk = (result?.sent !== false)` (`escalation.js:77`) therefore stays **false**. The record is upserted to `OohSmsLog` with `provider:'log'`, `dispatchOk:false`, and `sentToNumber` = `(configured)` or `(not configured)` — **never the raw number** (`escalation.js:65`). The outcome card (`flows.js:170-172`) renders the red **"Text not sent — phone the on-duty manager now"** variant, and the Zendesk `#ooh-p1-dispatch` corrective comment says NOT SENT. This honest no-op is locked by Test 11c and must remain true.

**State B — twilio mode (enabled).** With `provider='twilio'` and all three Twilio credentials present, `sendViaProvider()` POSTs to `https://api.twilio.com/2010-04-01/Accounts/{sid}/Messages.json` with HTTP basic auth and a 15-second timeout (`escalation.js:37-41`) and returns `{ provider:'twilio', sent:true }`. `dispatchOk` becomes **true** (`escalation.js:77`). The card (`flows.js:170-171`) renders the **"A text message has been sent to the on-duty escalation manager at HH:MM, with a direct link to ticket #{id}"** variant; `OohSmsLog` shows `dispatchOk:true`, `provider:'twilio'`, number still `(configured)`; and the Zendesk comment reads SENT. The message body is `OOH P1 — {siteName} ({siteNo}): {summary}. Ticket #{id}: {deep-link}` (`escalation.js:56`).

**State C — fail-closed (twilio selected, creds missing or invalid).** This is the safety net and must be verified as part of enablement — but verified in the **test suite / a non-production environment**, never by misconfiguring the live pod (see below and §4). If `accountSid || authToken || from` is falsy, `sendViaProvider()` **throws** "Twilio provider selected but not configured" (`escalation.js:36`); if Twilio rejects the request, `axios` throws. Either way the `try/catch` in `escalateP1` (`escalation.js:73-81`) catches it: **no crash**, `dispatchOk` stays **false** (it is initialised false at `escalation.js:69` and only set true on a genuine send at `:77`), and `raiseAlert('sms-dispatch-failed', …)` fires (`escalation.js:80`). The handler sees the **same "phone the manager now"** card as log mode — the escalation outcome is never blocked by an SMS failure.

**Where State C is proven — the one, unambiguous mechanism.** State C cannot be safely reproduced on the live system: the pre-flip pod runs `SMS_PROVIDER=log`, which takes the log branch (`escalation.js:44-47`) and **never reaches** the credential guard at `escalation.js:36`, so observing State C there is physically impossible; and the only other way to force it live — flipping to twilio with credentials deliberately absent — directly violates the load-before-flip ordering rule (§2), so it is prohibited. Therefore State C is verified as an **automated test** in `test/p1-dispatch-honesty.test.js`, which already runs in fixture mode with an intercepting axios adapter and **no network / no live send**. That suite already asserts the **invalid-credential/rejected-send** half of State C ("a twilio failure ⇒ dispatchOk false + an sms-dispatch-failed alert, escalation still returns"); the **missing-credential guard-throw** half (provider twilio with an empty `accountSid`/`authToken`/`from` → throw at `escalation.js:36` → caught → `dispatchOk` false, `sms-dispatch-failed` raised, honest card, no crash) is a small companion case to add to the same file. Running `npm test` green is the State C pass evidence. This keeps the prod runbook ordering sacrosanct while keeping State C a REQUIRED pass criterion.

**Invariant across all states:** SMS failure never blocks the P1 outcome (the ticket is still raised), and the raw recipient number is never persisted to the log, the artefact, or the Zendesk comment — status only.

## 4. End-to-end LIVE test design (defined here, executed after the flip)

Do not execute until Steps 1–4 of §2 are complete.

**Preconditions:**

- The five secret values loaded and `IOT_DASH_BASE_URL` = the live host (§1).
- `SMS_PROVIDER=twilio` on the running pod, pod healthy on `/healthz`.
- An **agreed test recipient or test window** — the configured recipient currently also acts as a Tier-1 tester (recorded in OOHDASH-73), so coordinate so a real out-of-hours-style text does not confuse a real person mid-shift. This de-confliction is a precondition, not an afterthought, and it has a **named owner: James (OOHDASH-73)** — he agrees the recipient/window and records it on the ticket before the test runs, so this is an assigned action, not an unowned "coordinate".
- A **stable, known test device/site** for the trigger, so a concurrent Stream A cellar reclassification cannot muddy the P1 (per the cross-stream hygiene note). `WRITES_DISABLED` state is irrelevant — this test enables no control.

**Steps:**

- Sign in as an OOH handler on the live site.
- Run a flow that yields a **system-decided P1** on the test site — one of the three current auto-P1 outcomes: kitchen equipment-off-during-service, fridge stock-at-risk, or contractor-on-site.
- Complete the outcome; start a stopwatch the moment the P1 is raised.
- Read the P1 outcome card — it should render the **"a text message has been sent"** variant, not "Text not sent".
- Confirm the recipient device receives the SMS, and that it carries a **working deep-link** to the just-created ticket.
- Click the deep-link; confirm it lands on the correct ticket detail in the IoT Support dashboard.
- Check the Zendesk `#ooh-p1-dispatch` corrective comment reads SENT.
- Check the `OohSmsLog` entry for the ticket: `dispatchOk:true`, `provider:'twilio'`, number shown as `(configured)`.

**Required fail-closed scenario (State C) — the primary safety property, NOT optional, and NOT run on prod.** The credential fail-closed path is a REQUIRED pass criterion, but it has **one** verification home: the **automated test suite** (`test/p1-dispatch-honesty.test.js`), optionally re-confirmed in a **staging/non-production** environment. It is **not** exercised by misconfiguring the live pod. The reason is spelled out in §3: the pre-flip `log` pod can never reach the credential guard (`escalation.js:36`), so State C is unobservable there; and a deliberately mis-ordered/mis-configured live flip is **prohibited** because it breaks the sacrosanct load-before-flip ordering (§2). The suite runs in fixture mode with an intercepting axios adapter — no network, no live send — and asserts: provider `twilio` with a credential missing or invalid → the guard throws (`:36`) or axios rejects → caught at `:73-81` → `dispatchOk:false`, honest "phone the manager" card, `sms-dispatch-failed` alert raised, no crash. `npm test` green **is** the State C evidence for this gate. This is the property the whole enablement rests on — if the suite does not hold it, the enablement is not safe to ship, regardless of the happy path passing.

**Pass criteria (all must hold):**

- SMS received in **under 60 seconds** of the P1 being raised.
- Message body contains a working deep-link resolving to the **correct** ticket.
- `dispatchOk:true` in the returned outcome, in `OohSmsLog`, and reflected as SENT in the Zendesk comment; card shows the sent variant.
- **No** `sms-dispatch-failed` alert raised on the happy path.
- The **raw recipient number is never persisted** (status only, `(configured)`).
- The `ESCALATION_ONDUTY_NAME` shown on the sent card, in `OohSmsLog` and in the Zendesk comment is the **real on-duty person's name**, not the generic "On-duty escalation manager" default — proving the name was loaded correctly.
- **Deep-link resolves to the correct LIVE ticket (REQUIRED):** tap the link in the received SMS and confirm it opens the **correct** ticket detail in the **live** IoT Support dashboard. This is the required catch for a wrong/UAT `IOT_DASH_BASE_URL`, which does **not** fail closed (§1 Change 2) — a text that "sent" but carries a dead or wrong link is a **fail**.
- **Fail-closed (REQUIRED, proven in the test suite — not on prod):** the credential fail-closed behaviour — provider twilio with a credential missing or invalid → handler sees the safe **"phone the on-duty manager now"** card, app does **not** crash, `dispatchOk` stays **false**, no dishonest SENT is recorded, and an `sms-dispatch-failed` alert **is** raised — is a required pass criterion, evidenced by `npm test` green over `test/p1-dispatch-honesty.test.js` (and optionally a staging re-run). It is **not** verified by misconfiguring the live pod, which would violate the load-before-flip ordering (§2/§3).
- **Responsive/mobile rendering (REQUIRED sign-off):** on a phone-width viewport, confirm all three P1 outcome-card states render cleanly — the sent variant (timestamp + deep-link must both be readable and the deep-link tappable), the log/no-send variant, and the fail-closed variant. The handler journey includes reading this card on a mobile device out of hours, so a broken sent-variant on mobile is a fail.

**Cleanup:** the test raises a real urgent Zendesk P1 ticket — close/delete it afterwards and note it was internal-only, as prior discovery walks did with their test tickets.

## 6. On-duty recipient — named owner and rotation runbook (proposed — pending James's confirmation at gate)

`ESCALATION_ONDUTY_NUMBER` and `ESCALATION_ONDUTY_NAME` are a **single static pair** the code reads at send time; there is no rota logic. That makes a stale value a **silent failure mode**: if the number belongs to someone off shift, sick or on holiday, the code still returns `dispatchOk:true` and posts a **SENT** Zendesk comment — the text simply lands with the wrong person and **nothing alerts**. This section closes that gap with a named owner and a manual rotation process. It is **proposed pending James's confirmation at gate.**

**Named owner.** **IoT Support (Sam Day's team) owns `ESCALATION_ONDUTY_NUMBER` and `ESCALATION_ONDUTY_NAME`** — they are accountable for the value being correct and current, and for the name being a **real person**, never the generic "On-duty escalation manager" default.

**Rotation runbook (owned by IoT Support / ops), for shift change, sickness or holiday:**

- IoT Support determines who the on-duty escalation manager is for the period, and their contact number.
- Because secret-write is **Spencer-only** (James's scoped account cannot write it), IoT Support **requests the secret update via Spencer**, giving the new number and the new real name for `ESCALATION_ONDUTY_NUMBER` / `ESCALATION_ONDUTY_NAME`.
- Spencer updates `ooh-dashboard-secrets` and confirms the change back in writing (as in §2 Step 2).
- **Verification step (mandatory, and timely):** after the pod picks up the change, IoT Support confirms the **right person is reachable** on the configured number — e.g. a controlled test P1 or an agreed check text — so a mistyped or stale number is caught immediately rather than at the next real P1. The outcome card / log now showing the **correct real name** is the visible confirmation. **Timeliness matters:** because a stale value fails silently (a "successful" send to the wrong person, no alert), this verification must be run **at the point of each rotation**, not deferred — a rotation that changes the secret but skips the check re-opens the exact silent-failure gap this section exists to close.

**Backup / break-glass — Spencer is not a single point of failure (proposed — pending James's confirmation at gate).** Rotation depends on Spencer, the only secret-writer, in a **24/7** system; if Spencer is unavailable (out of hours, on leave, sick) a needed rota change would otherwise be stuck, leaving a wrong on-duty number live with no way to correct it. Two paths close that gap:

- **Durable fix — a second secret-writer.** Grant a second named person write access to `ooh-dashboard-secrets` so secret loads and rotations are never blocked on one individual. This ties directly to the standing access-decouple ask and is the preferred permanent answer.
- **Interim break-glass (emergency only, documented).** In an emergency, James can self-serve an env override of the recipient with `kubectl set env deployment/ooh-dashboard ESCALATION_ONDUTY_NUMBER=<num> ESCALATION_ONDUTY_NAME="<real name>"` (his scoped account holds the env-patch verb). This is a **last resort**, explicitly noting its costs: it **temporarily exposes the raw number in the deployment env** (not in the managed secret), and it **creates git-versus-cluster drift**. It **must be reverted** — the env override removed and the value restored to the secret — **as soon as Spencer (or the backup writer) can reload the secret**. Same single-key discipline as §2 Step 3 applies: never include `WRITES_DISABLED` in the command.

**Future enhancement (explicitly out of scope for this config + secret stream):** a schedule-driven rota lookup — the app resolving the current on-duty manager from an IoT Support shift schedule instead of a static secret — would remove the manual request-via-Spencer step and the staleness risk entirely. That is application work (a code change), not config, and is deliberately **not** part of this enablement.

**Near-term excellence targets (future, out of scope for this stream — noted so they are not lost):**

- **Manager-acknowledgment loop.** Today the P1 SMS is fire-and-forget: `dispatchOk:true` proves the text was *sent*, not that the manager *saw and accepted* it (the `OohP1AckAt`/`OohP1AckBy` fields on `OohSmsLog` exist but are set only from the dashboard/Admin, not by the recipient). A near-term excellence target is an acknowledgment loop — the on-duty manager confirming receipt (e.g. a reply keyword or an ack link) so an unacknowledged P1 can be re-chased. This is application work, deliberately not in this config + secret stream.
- **Call-to-action cue in the SMS body.** The current body is `OOH P1 — {siteName} ({siteNo}): {summary}. Ticket #{id}: {link}` (`escalation.js:56`) — it states the incident but not the expected action. A short call-to-action (what the manager is expected to do, and by when) would sharpen the recipient experience. Because the template lives in `escalation.js`, changing it is a **code change** — recorded here as a **recommended near-term follow-up**, not part of this config + secret enablement.
